# 농업 문서 요약 및 질의응답 서비스 답안 해설

> 코드 답안은 `농업_문서_요약_및_질의응답_서비스_답안예제.py`를 참고한다.

## 1. 핵심 채점 포인트

| 항목 | 확인 내용 |
|---|---|
| PDF 활용 | 현재 폴더 PDF를 로드하여 텍스트 추출 |
| 청킹 | `chunk_size` / `chunk_overlap`으로 분할 |
| 임베딩 | OpenAI Embeddings 사용 |
| 벡터 검색 | FAISS로 Top-K 유사 청크 검색 |
| RAG 질의응답 | 검색 결과를 컨텍스트로 LLM 답변 생성 |
| 요약 | 주제 요약 또는 문서 샘플 요약 제공 |
| 근거 표시 | 출처(파일명/페이지) 또는 검색 청크 표시 |
| 인덱스 저장 | 로컬 저장/로드 가능 (경로 이슈 대응 포함) |
| UI | Streamlit으로 실행 가능 |

## 2. 파이프라인 해설

```text
PDF → 페이지 텍스트 추출 → 청크 분할
    → OpenAI Embedding → FAISS 인덱스(메모리)
    → (선택) ASCII 안전 경로에 저장
    → 질문 Embedding → 유사 청크 검색
    → (컨텍스트 + 질문) → LLM 답변/요약
```

### 왜 페이지 제한(`max_pages`)이 필요한가?

제공 PDF는 파일당 200~370페이지 수준이다.  
수업 시간·임베딩 비용·대기 시간을 고려해 파일당 20~50페이지로 제한하는 것이 실용적이다.

### 왜 overlap을 두는가?

청크 경계에서 문장이 잘리면 의미가 끊긴다.  
overlap으로 앞뒤 문맥을 일부 겹쳐 검색 품질을 안정화한다.

## 3. Windows FAISS 한글 경로 이슈 (답안 반영 사항)

### 증상

인덱스 생성 중 아래와 유사한 오류가 발생할 수 있다.

```text
인덱스 생성 실패:
Error in faiss::FileIOWriter ...
could not open ...\faiss_index\index.faiss for writing: Illegal byte sequence
```

### 원인

- Windows용 FAISS(C++ IO)는 **한글 등 비ASCII 경로**를 열지 못하는 경우가 많다.
- 프로젝트 폴더명이 `스마트 농업...`, `농업 문서...`처럼 한글이면  
  `프로젝트/faiss_index`에 저장할 때 실패한다.
- 임베딩·FAISS 메모리 구축까지는 성공해도, **파일 저장 단계**에서 오류가 난다.

### 답안 코드의 대응

`resolve_index_dir()`로 저장 경로를 결정한다.

```text
1) 프로젝트 경로가 ASCII이면
   → ./faiss_index 사용

2) 프로젝트 경로에 한글이 있으면
   → %TEMP%/agri_rag_faiss_<해시> 사용
     (예: C:\Users\...\Temp\agri_rag_faiss_d8b9df14d4)
```

추가 방어 로직:

- 저장에 실패해도 **메모리 인덱스는 유지**하여 질의응답/요약을 계속 사용 가능
- 사이드바에 실제 인덱스 저장 경로를 표시
- "저장본 로드"는 위 ASCII 안전 경로에서 읽음

> 채점 시: 프로젝트 폴더에 `faiss_index`가 없어도  
> TEMP 경로에 인덱스가 저장되면 정상 구현으로 본다.

## 4. 테스트 질문별 기대 동작

### (1) 딸기 정식 시기와 주의점은?

- 기대: 딸기 관련 청크가 Top-K에 포함
- 답변: 정식 시기/정식 후 관리 포인트 요약
- UI: 근거 청크에 `농업기술길잡이40_딸기.PDF` 등이 보임

### (2) 고구마 저장 방법은?

- 기대: 고구마 문서의 저장/큐어링 관련 내용 인용
- 답변: 온도·습도·저장 관리 요점

### (3) 사과 병해충 방제 방법을 알려줘

- 기대: 사과 문서 기반 방제 안내
- 답변: 병해충명과 방제 포인트를 근거와 함께 제시

### (4) 우주선은 어떻게 만드나요?

- 기대: 관련 청크 유사도가 낮거나 내용 불일치
- 답변: "제공된 문서에서 확인되지 않습니다" 유형의 안전 응답

## 5. 확인 질문 모범 답안

### Q1. RAG를 쓰지 않고 LLM만으로 PDF 내용을 답하면?

모델이 문서 원문을 직접 보지 못해 환각이 발생하기 쉽다.  
RAG는 실제 문서 조각을 검색해 근거 기반으로 답하게 한다.

### Q2. chunk_size / chunk_overlap을 잘못 잡으면?

- 너무 큼: 검색 단위가 거칠어지고 토큰 비용 증가
- 너무 작음: 문맥이 부족해 답변 품질 저하
- overlap 과다: 중복 증가, 인덱스 비대화
- overlap 과소: 경계 정보 유실

### Q3. FAISS는 키워드 검색인가?

아니다. 임베딩 벡터 공간에서 **의미 유사도**를 기준으로 검색한다.  
동의어·유사 표현도 찾을 수 있다.

### Q4. 검색된 청크를 LLM 프롬프트에 넣는 이유는?

LLM에 "검증 가능한 근거"를 제공하기 위해서다.  
검색 결과(컨텍스트)를 넣어야 문서 기반 답변과 출처 제시가 가능하다.

### Q5. 문서에 없는 질문은?

컨텍스트에 없으면 추측하지 말고  
"문서에서 확인되지 않는다"고 답하도록 시스템 프롬프트를 강제하는 것이 안전하다.

## 6. 실행 방법

```bash
pip install -r requirements.txt
streamlit run 농업_문서_요약_및_질의응답_서비스_답안예제.py
```

제출 형식에 맞출 경우:

```bash
copy 농업_문서_요약_및_질의응답_서비스_답안예제.py app.py
streamlit run app.py
```

### 인덱스 생성 체크리스트

1. 사이드바에서 PDF 2개 이상 선택
2. `max_pages`를 20~30으로 설정
3. **인덱스 생성** 클릭
4. 성공 메시지와 함께 저장 경로 확인  
   - 한글 프로젝트 경로면 TEMP 하위 경로가 표시됨
5. 질의응답/요약 탭에서 테스트
6. 앱 재실행 후 **저장본 로드**로 재사용 확인

## 7. 실습 팁

1. 처음에는 PDF 2개, `max_pages=20~30`으로 인덱스를 만든다.
2. 인덱스가 만들어진 뒤 질의응답/요약을 테스트한다.
3. "저장본 로드"로 재실행 시간을 줄일 수 있다.  
   (저장 위치는 사이드바의 인덱스 저장 경로를 본다.)
4. `Illegal byte sequence` 오류가 나면 한글 경로 문제이므로  
   ASCII TEMP 경로 저장 방식이 적용됐는지 확인한다.
5. 답변이 빈약하면 Top-K를 늘리거나, 해당 주제 페이지가 `max_pages` 안에 있는지 확인한다.
6. 저장이 실패해도 같은 세션에서는 메모리 인덱스로 질의응답이 가능하다.
